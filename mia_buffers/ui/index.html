    Training on a MIA buffer

    A buffer is a pool of training crops drawn from the catalogued datasets that match a spec. The spec is a short YAML file, and it defines both ends of the buffer. On the input side it says which datasets qualify. On the output side it says how crops are presented to the model: the patch size and pyramid levels, the channels, the normalization, the weighting between datasets, and how volumes are split into train, validation and test. The system plans the pool, downloads and converts the datasets it already knows how to read, and serves crop descriptors over HTTP; a Python dataset class turns them into tensors in the training process. Starting a buffer and approving it are done with labels on a GitHub issue, and the system reports back in that issue's comments. This web UI is read-only: it shows the catalog, the buffers and the cache, and needs no login.

    The whole loop

    Step 1. The spec

    The Datasets tab builds a spec from its filters: dimensionality, modality, licence, whether annotations are required, the smallest array accepted, the patch size and pyramid levels, and the weighting between datasets. Each change is planned against the catalog on the server, so the counts shown are the plan that spec produces.

    • Where records leave counts the datasets each rule removes. The last rule, not prepared, means a dataset fits the spec but no reader exists for its files yet; the other rules are the spec's own filters.
    • Fitting datasets by modality and Weight share show the composition of the pool and of the draws. The weighting temperature runs from uniform over modalities (0) to proportional to each dataset's capacity (1).
    • Request preparation opens an issue that hands the fitting, unprepared datasets to the preparation pipeline. Each one is an agent run that writes and verifies a reader for that dataset's files; some stop with a question for a human. Progress is on the Preparation tab. A buffer plans over prepared datasets only, so a buffer started now uses what is prepared now, and a later round picks up the rest.
    • Download spec YAML saves the spec as a file, for editing by hand or for keeping with an experiment.

    The fields of a spec that are usually edited:

    name: my-2d-nuclei                      # free; names the buffer on the page
catalog: {repo: …, ref: <commit>}       # pinned by the page: the plan is reproducible
select:
  where:
    dims: {in: [2D]}
    modality: {in: [fluorescence, brightfield]}
    license: {in: [CC0-1.0, CC-BY-4.0], allow_unknown: false}
    annotations: {required: true}
sampling:
  patch: {2D: {y: 256, x: 256}, c: 1}   # crop edges in pixels at level 1; one channel per crop
  levels: [1, 2, 4]                     # the pyramid levels each crop is served at
  weighting: {scheme: temperature, over: [modality, dataset], temperature: 0.5}
  normalize: {method: percentile, range: [1, 99], scope: volume}
splits:
  fractions: {train: 0.8, val: 0.1, test: 0.1}
ready:
  min_fraction: 0.5                     # how much of each weighting group must be servable before the board says "ready"

    Step 2. Start the buffer

    Open buffer issue on the Datasets tab opens a prefilled issue in the buffers repository: the spec in a YAML block, with the catalog commit pinned. Creating the issue runs nothing.

    Adding the label buffer:go starts the buffer. The poller picks the label up within a couple of minutes and removes it once the signal is accepted; the first comment follows. From then on every stage change is a label the system sets and a comment that says what happened and what, if anything, it needs from a human.

    label a human addswhat it does
    buffer:goPlan, download, stage, then stop once at buffer:staged. Also how a round is started over after editing the spec: the earlier round's buffer is retired.
    buffer:planLike buffer:go, but also stop after the plan, before any job runs.
    buffer:approveContinue from whichever gate the issue is at: the plan, or the staged board.
    buffer:keepAn idle buffer stays; back to ready.
    buffer:retireRelease the buffer's staged data now. Closing the issue does the same.
    the system setsthe buffer is
    buffer:planning → buffer:plan-reviewresolving the spec; the plan is posted (the pool, one row per dataset, with weights). A buffer:plan round waits here for buffer:approve.
    buffer:sourcingdownloading and converting, several datasets at a time. One comment per dataset as it lands or fails.
    buffer:stagedno job left to run; the board is posted. Waiting for buffer:approve.
    buffer:readyserving. The comment holds the Python cell with the buffer id filled in.
    buffer:idle · buffer:retirednobody drew from it for a while (default 72 hours) · its data is released.
    buffer:needs-humanstopped. The comment says why; the usual answer is an edited spec and buffer:go again.

    Only someone with write access to the repository can drive an issue; a label from anyone else is removed with a note.

    Step 3. Read the board, then approve

    Sourcing runs until no dataset has a job left. The issue then moves to buffer:staged and gets the board: each dataset's outcome (with the error of one that failed), each weighting group's servable share against ready.min_fraction, volumes per split, bytes on disk, and which datasets are still waiting on something.

    Approve. buffer:approve serves the buffer as the board shows it. A dataset that failed stays out; one that is waiting keeps its place and joins when it lands, with a new board comment. The share each group has at the approve becomes the floor it is judged against afterwards, so a partial buffer accepted on purpose is not later reported as degraded. No job runs between the approve and buffer:ready.

    Or edit and go again. Editing the YAML in the issue body and adding buffer:go retires the staged buffer and plans a new round from the edited spec. Converted pyramids stay in the shared cache, so a second round over the same datasets skips the conversion.

    • Waiting on a drop. Some datasets sit on hosts no job may reach. The comment lists the files to place by hand in the dataset's incoming/ directory; once the listing stops changing, the worker takes them into the cache.
    • Waiting for a quota or a lock. The cache is full, or another buffer is converting the same dataset. Both clear on their own.
    • Day limit. A group with nothing servable after sourcing.dataset_timeout_days (default 14) drops its waiters; with nothing servable at all the issue stops at buffer:needs-human.
    • Automatic approve. plan: {auto_approve: true} in the spec approves without a human when every group meets min_fraction. A short group still waits for one.

    Step 4. Train

    The buffer:ready comment names the buffer id (i<issue>-e<event>) and gives this cell. It runs in the harness environment of the mia-snippets checkout, with this repository on the Python path and torch and muvit installed:

    from mia_buffers.client import BufferDataset

URL, TENSORIZERS = "<service url>", "<mia-snippets checkout>"   # or export MIA_BUFFERS_TENSORIZERS
train_ds = BufferDataset(URL, "<buffer id>", "train", n_samples=4000, tensorizers=TENSORIZERS)
val_ds = BufferDataset(URL, "<buffer id>", "val", tensorizers=TENSORIZERS)

loader = DataLoader(train_ds, batch_size=32, num_workers=8, collate_fn=BufferDataset.collate)
model = MuViTMAE2d(in_channels=train_ds.n_channels, levels=train_ds.levels, ...)
    • Train is a stream. Each item is a fresh crop drawn by the service under the spec's weighting; n_samples is the length of one virtual epoch and the index is ignored. Val and test replay a frozen list that is the same every epoch and every run.
    • The service serves descriptors, not pixels. A descriptor names the pyramid, the window, the channels and the normalisation bounds. The training process reads the OME-Zarr pyramid from shared storage and tensorises it, so the load of a DataLoader with many workers falls on the training node. Each worker registers itself as a consumer, listed on the Buffers tab.
    • What a sample holds. The image at each level in sampling.levels, the label layers the dataset has, and meta with the record, the voxel size and the crop's position in physical units. A buffer mixes datasets whose label layers differ, which is why the custom collate is needed: a batch keeps the keys every sample has.
    • What is pinned. The buffer records the catalog commit, the spec hash, the plan hash and the commit of the conversion code. A checkout at a different commit raises on construction; allow_recipe_mismatch=True turns that into a warning.
    • Before the approve the service answers 409 and the client raises BufferNotApproved. After a retire it answers 410. A split with nothing servable yet raises BufferEmpty.

    Step 5. During training, and afterwards

    The Buffers tab lists every buffer with its latest event; a buffer's own page has the board, the volumes per split, the consumers seen, the draws per day and a health line. After buffer:ready the issue changes only when one of these happens:

    • Degraded. When a group's servable share falls under the floor set at the approve (a pyramid was evicted or lost), the issue says so and the worker stages the missing datasets again from the cache.
    • Idle. No consumer for idle.hours (default 72) puts buffer:idle on the issue; buffer:keep returns it to ready. After retire_after_days (default 14) more days without a draw the keeper retires the buffer and its space is reclaimed.
    • Closed. Closing the issue stops its workflow and retires its buffer; the label becomes buffer:retired. Reopening it and adding buffer:go runs the same spec again, reusing what is still in the cache.

    Words the pages use

    wordmeaning
    dataset, recordone entry of the catalog: a published dataset with its files, licence, modality and annotations described. The code and the catalog say record for the entry and its id; the pages say dataset.
    prepareda record with an approved reader and verified sample crops, produced by the preparation pipeline. Only prepared records enter a plan.
    buffer, roundone served pool of crops for one spec. An issue runs one round at a time; each buffer:go starts a new round with a new buffer id, and the earlier buffer is retired.
    weighting groupthe datasets that share the first key of weighting.over, a modality for instance. min_fraction and the floors are per group.
    stagedconverted: a dataset's volumes rewritten once as immutable OME-Zarr pyramids in the shared cache, reused by every buffer that needs the same geometry.
    crop, levela crop is one training window, served at each pyramid level the spec lists, all centred on the same point: level 1 is full resolution, level 2 half, and so on.
    splittrain, val or test. Volumes are assigned by the spec's fractions and seed; a record in holdout_ids is all test.
    keeperthe background pass that watches quotas, idle buffers and lost pyramids. It is the only thing that deletes.

    MIA Training Buffers

    The system is two pipelines that share one registry. mia-data turns a catalog record into a prepared dataset, which means an approved binding and verified crops on shared storage. mia-buffers turns a buffer spec into served crops. It plans over prepared datasets only, fetches the raw files once into a shared cache, stages each volume as an immutable OME-Zarr pyramid, and registers each pyramid with buffer-api, the one service that picks every crop. Training jobs pull crop descriptors from the service and read the pyramids themselves. GitHub issues and labels remain the way a human starts or approves anything. A read-only web UI, served by buffer-api at its own address, shows the whole state in four views (datasets, buffers, cache and preparation) and carries these documents as a fifth.

    1. System layout

    One host runs everything that holds a credential: Temporal, the two workers and buffer-api. Jobs run on the cluster and see only files. In the figure, lines run in the gutters between columns, and each later figure drills into one part of this one.

    2. Two workflows around shared resources

    In the figure, data preparation runs along the top and buffering along the bottom. Dashed arrows say which resource a step reads or writes, and the columns line up so that each dashed arrow stays in its own lane.

    3. How a dataset becomes prepared

    A dataset is prepared when mia-data has published a binding and a manifest for it. A buffer plans over prepared datasets only, and asking for more datasets to be prepared is its own, explicit request. Preparation judges nothing about who may use a dataset. Licence, modality, organism, annotations and fit at a given patch size and set of levels are all filters of a buffer spec, and the planner evaluates them per spec. A dataset of 60-pixel images is therefore prepared like any other and simply fails the fit rule of a 256-pixel buffer (spec §12). The only place preparation stops is a needs-human state.

    3b. The review loop

    Every set of crops waits at data:review, including a set made from a snippet PR. data:approve publishes the set the reviewer looked at. When that set came from a PR head, the worker first has autodev merge that head, and the same files are published under the merge commit. data:reject sends every comment the reviewer wrote on the issue since the crops report to the agent. When the round is following a PR, the comments go as /revise on that PR. Otherwise they go as a new mia-snippets issue asking for a snippet that supersedes the one at fault, because a merged snippet is never edited. The next set of crops comes back to review, and the loop continues until the reviewer approves (spec §14).

    4. Lifecycle of a buffer issue

    A buffer issue carries one buffer:* label at a time. Humans add five of the labels, and the worker and the keeper set every other transition. Since v0.6 a round is staged before it asks for approval. buffer:go asks once, at staged, and buffer:plan asks after the plan as well.

    5. Sourcing one dataset

    Once a round is planned, the worker sources every dataset in the pool, heaviest first, so the datasets that supply the most crops are staged earliest. Each dataset passes through the two phases shown in figure 5, a fetch and a stage. A record's raw cache is written by one job at a time, across both pipelines and any number of buffers. A lock file on the host's local disk enforces that.

    6. The cache and its keeper

    The cache is two shared roots, the raw root and the staged root, and both are reference-counted through the registry. Nothing in the service deletes. Only the keeper, which runs inside the buffers worker, removes a directory.

    7. Serving

    Train consumers get a stream of crops, and val and test consumers get a frozen list. Both kinds read the pixels from shared storage themselves.

    8. What a crop is

    The service hands out descriptors, not pixels. Whoever tensorises a crop derives one pixel box per level from the descriptor and reads it from the pyramid. The example in figure 8 uses the U937 confocal record, with 45 nm pixels, 256-pixel patches and levels 1, 2 and 4.

    9. Where things live

    One configuration file serves every service on the host. Anything that needs a working lock lives on host-local disk, and everything a job or a consumer reads lives on shared storage.

    mia.yaml                                 one file: shared sections, then services.<name> overlays

<local_root>/                            host-local disk (file locks and SQLite do not work on NFS)
  locks/raw/<record>                     one writer per raw cache · owner, heartbeat, TTL 15 min
  locks/snapshot/<sha>                   one extraction per pinned commit
  service/buffers.sqlite                 the registry · backed up every 30 min to state/

    What is not built

    • Remote mode: crop workers beside the service that tensorise and return tensors over HTTP. Local mode, where the training job reads the pyramid, is the only mode.
    • The evaluation step: an agent that writes evaluation.yaml (voxel size, channel meanings, a quality verdict) beside the binding. The config switch exists, but the job does not.
    • Identity on the service: the web UI cannot start a buffer or a request by itself. When a proxy or token layer lands in front of buffer-api, the same buttons can call the API directly.
    • Several worker hosts: the lock directory assumes one host. The upgrade is a lease table in the registry with the same four calls.
